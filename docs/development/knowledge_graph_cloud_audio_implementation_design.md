# Knowledge Graph Cloud Audio: Implementation Design

_Status: Initial design; see the deployment runbook for implemented behavior_

_Last updated: 19 July 2026_

_Related documents:_

- [knowledge_graph_cloud_audio_deployment.md](knowledge_graph_cloud_audio_deployment.md)

## 1. Purpose

This document defines how the existing Knowledge Graph interaction should play speech audio generated by a cloud service instead of always synthesizing the returned answer locally with Acapela.

The design supports both Knowledge Graph entry paths:

1. **Prompted question:** The user says “I have a question,” Vector prompts the user, then opens a wake-wordless Knowledge Graph stream for the actual question.
2. **Bypass question:** The user asks a complete question in the initial wake-word utterance, and the intent graph returns a Knowledge Graph answer immediately.

Both paths converge on the same answer renderer. Cloud audio is preferred when available; the existing answer text remains mandatory for local-TTS fallback.

## 3. Goals

### 3.1 Functional goals

- Play Knowledge Graph answer audio generated by a cloud service.
- Preserve `answer` text for fallback, logging policy, and diagnostics.
- Support both prompted and bypass Knowledge Graph paths.
- Support a low-risk fully-buffered mode first.
- Support low-latency streaming playback using the same protocol later.
- Preserve existing Knowledge Graph animations and interruption behavior.
- Cancel cloud audio when the behavior is interrupted.
- Fall back to local TTS when cloud audio is unavailable or fails before useful playback.
- Keep current behavior unchanged when the feature is disabled.

### 3.2 Engineering goals

- Do not put a complete PCM response inside `IntentResult.parameters`.
- Do not permanently route internal voice output through the public SDK gRPC API.
- Reuse the Wwise `StreamingWavePortalPlugIn` and proven PCM conversion patterns.
- Keep cloud-audio ownership separate from SDK audio and local TTS.
- Correlate all asynchronous messages using a response ID.
- Reject stale, duplicate, and out-of-order audio chunks.
- Bound memory, response length, queue depth, and timeouts.
- Make the renderer extensible to other conversational features later.

## 4. Non-Goals

The first implementation does not include:

- General cloud audio for every user intent
- Natural speech barge-in
- Full duplex or acoustic echo cancellation
- Mixing local TTS and cloud speech simultaneously
- Stereo playback
- Arbitrary remote audio URLs fetched by the robot
- Persisting audio across process restart
- Reusing Alexa media players directly
- Replacing local Knowledge Graph ready prompts or earcons
- Compressed audio decoding in the first release

## 5. Design Summary

Use a dedicated Knowledge Graph response-audio lifecycle:

```text
Knowledge service / cloud TTS
       |
       | answer text + response metadata + PCM chunks
       v
vic-cloud
       |
       | CloudMic responseAudioStart/chunk/end/error over ai_sock
       v
vic-engine CloudResponseAudioCoordinator
       |
       | RobotInterface CloudAudioPrepare/chunk/complete/cancel
       v
vic-anim CloudAudioComponent
       |
       | dedicated StreamingWavePortal plugin ID + Wwise event
       v
speaker
```

The Knowledge Graph behavior receives answer text through its normal user intent and receives audio readiness/progress through `CloudResponseAudioCoordinator`, correlated by `responseId`.

The transport is always chunked. Playback policy determines whether audio is:

- **BufferedComplete:** fully received before playback starts; recommended first milestone.
- **Streaming:** started after a prebuffer while remaining chunks arrive; second milestone.

## 6. Why Chunked Transport for Both Modes

A complete 16 kHz mono 16-bit PCM answer uses approximately 32 KB per second:

$$
16000\ \text{samples/s} \times 2\ \text{bytes/sample} = 32000\ \text{bytes/s}
$$

`IntentResult.parameters` has a 65,535-byte encoded-length limit, and the engine cloud server reads datagrams into a 4,096-byte buffer:

- [`clad/src/clad/cloud/mic.clad`](../../clad/src/clad/cloud/mic.clad#L45-L49)
- [`engine/aiComponent/behaviorComponent/behaviorComponentCloudServer.cpp`](../../engine/aiComponent/behaviorComponent/behaviorComponentCloudServer.cpp#L54-L66)

Embedding audio in intent JSON would therefore:

- Limit answers to roughly two seconds before encoding overhead.
- Increase copies and JSON/base64 overhead.
- Risk datagram truncation.
- Prevent useful sequencing and cancellation.

Chunking avoids those limitations. In `BufferedComplete` mode, chunks are still transported incrementally but playback waits for `responseAudioEnd`.

## 7. Audio Contract

### 7.1 Initial format

The first release accepts only:

| Property | Value |
|---|---|
| Encoding | Signed PCM |
| Sample representation | 16-bit little-endian |
| Channels | 1 |
| Sample rate | 16,000 Hz preferred; 8,000–16,000 Hz accepted |
| Chunk payload | Maximum 1,024 bytes |
| Maximum response duration | 30 seconds, configuration-driven |
| Maximum response bytes | 960,000 bytes at 16 kHz/30 seconds |

The existing SDK stream validates 8,000–16,025 Hz and converts 16-bit little-endian PCM into the Wwise streaming container:

- [`animProcess/src/cozmoAnim/audio/sdkAudioComponent.cpp`](../../animProcess/src/cozmoAnim/audio/sdkAudioComponent.cpp#L160-L190)
- [`animProcess/src/cozmoAnim/audio/sdkAudioComponent.cpp`](../../animProcess/src/cozmoAnim/audio/sdkAudioComponent.cpp#L195-L229)

The new component should reuse this conversion logic through a common player rather than duplicate it permanently.

### 7.2 Future formats

Opus can be added later for lower network bandwidth. It is not part of the first release because it requires:

- An on-robot decoder
- Decoder lifecycle and error handling
- Packet-loss behavior
- Jitter buffering
- Resampling rules
- Additional CPU and memory validation

The message schema includes an encoding field from the start so adding Opus does not require redesigning correlation and lifecycle semantics.

## 8. Response Identity and Metadata

Every cloud-audio answer has a globally unique or boot-unique `responseId`.

Extend `UserIntent_KnowledgeResponse`:

```clad
structure UserIntent_KnowledgeResponse
{
  string answer,
  string query_text,
  string response_id,
  bool cloud_audio_available
}
```

The answer text remains mandatory. `cloud_audio_available` means the service intends to provide audio, not that playback is guaranteed.

Recommended cloud metadata:

| Field | Purpose |
|---|---|
| `response_id` | Correlates intent, chunks, playback, cancellation, and fallback |
| `answer` | Local-TTS fallback text |
| `query_text` | Existing diagnostics/intent data |
| `audio_available` | Signals whether the engine should wait briefly for cloud audio |
| `audio_encoding` | PCM16LE initially |
| `sample_rate_hz` | Playback format |
| `channels` | Must be one initially |
| `total_frames` | Optional validation and progress estimate |
| `duration_ms` | Optional timeout and UX estimate |

## 9. `CloudMic` IPC Changes

Add response-audio messages to the editable schema:

- [`clad/src/clad/cloud/mic.clad`](../../clad/src/clad/cloud/mic.clad)

Proposed structures:

```clad
enum uint_8 ResponseAudioEncoding {
  Pcm16Le,
  Opus
}

enum uint_8 ResponseAudioErrorType {
  Provider,
  InvalidFormat,
  TooLarge,
  Timeout,
  Cancelled,
  Transport
}

structure ResponseAudioStart {
  string responseId,
  ResponseAudioEncoding encoding,
  uint_32 sampleRateHz,
  uint_8 channels,
  uint_32 totalFrames,
  bool totalFramesKnown
}

structure ResponseAudioChunk {
  string responseId,
  uint_32 sequenceNumber,
  uint_8 data[uint_16]
}

structure ResponseAudioEnd {
  string responseId,
  uint_32 finalSequenceNumber
}

structure ResponseAudioError {
  string responseId,
  ResponseAudioErrorType error,
  string details
}
```

Add to `CloudMic::Message` as cloud-to-engine variants:

```clad
ResponseAudioStart responseAudioStart,
ResponseAudioChunk responseAudioChunk,
ResponseAudioEnd responseAudioEnd,
ResponseAudioError responseAudioError
```

### 9.1 Message size rules

- `ResponseAudioChunk.data` must be capped at 1,024 bytes by the sender.
- Total packed message size must remain below the 4,096-byte engine receive buffer.
- `responseId` should be short, for example 16 bytes or a compact UUID string.
- Sequence numbers start at zero.
- Empty chunks are invalid.
- PCM chunks must contain an even number of bytes.

### 9.2 Ordering

Expected order:

```text
IntentResult(response_id, answer, audio_available=true)
ResponseAudioStart(response_id)
ResponseAudioChunk(response_id, 0)
...
ResponseAudioChunk(response_id, N)
ResponseAudioEnd(response_id, N)
```

The audio start may arrive before or after the intent because they travel asynchronously. The engine coordinator stores either side briefly and joins them by `responseId`.

The coordinator must not assume Unix datagram ordering across separate connections or process restarts. Sequence validation remains mandatory.

## 10. Cloud Backend and `vic-cloud` Changes

### 10.1 Backend contract

The Knowledge service must continue returning:

- `SpokenText`
- `QueryText`
- `CommandType`

It additionally returns or initiates:

- `responseId`
- Audio metadata
- Audio chunks or a stream from a cloud TTS service

Two provider architectures are acceptable:

#### Preferred: backend streams answer audio

The Knowledge/conversation backend emits answer metadata and audio events on a response stream. This provides the lowest latency and a single authenticated service boundary.

#### Transitional: `vic-cloud` requests cloud TTS

`vic-cloud` receives `SpokenText`, then calls a configured cloud TTS endpoint and forwards returned PCM. This is easier when the current Knowledge API cannot return audio, but it adds another cloud request and keeps TTS-provider logic in the robot cloud process.

The design below works with either source because `vic-cloud` normalizes both to `ResponseAudioStart/Chunk/End/Error`.

### 10.2 Stream receiver changes

The current `stream.Receiver` only reports final intent, error, stream open, and connection result. Add response-audio callbacks or one typed response event channel:

```go
type ResponseAudioReceiver interface {
    OnResponseAudioStart(*cloud.ResponseAudioStart)
    OnResponseAudioChunk(*cloud.ResponseAudioChunk)
    OnResponseAudioEnd(*cloud.ResponseAudioEnd)
    OnResponseAudioError(*cloud.ResponseAudioError)
}
```

Affected area:

- `cloud/internal/voice/stream/types.go`
- `cloud/internal/voice/stream/context.go`
- `cloud/internal/voice/process.go`

### 10.3 Process lifecycle

The current `voice.Process` closes `strm` immediately after receiving the final intent:

- [`cloud/internal/voice/process.go`](../../cloud/internal/voice/process.go#L272-L289)

For backend-streamed audio, separate **microphone input completion** from **response output completion**:

1. Final intent arrives.
2. Send `stopSignal` to `vic-anim`; microphone capture ends.
3. Send `IntentResult` to engine immediately.
4. Close only the upstream audio-send side if necessary.
5. Continue receiving response-audio events.
6. Close the response stream after `ResponseAudioEnd/Error`.
7. Apply an audio-response timeout.

If the cloud TTS request is independent from Chipper, the Chipper stream may close after the intent while a separate audio goroutine continues using the same `responseId` and cancellation context.

### 10.4 Intent parameters

Update `sendKGResponse` to include:

```json
{
  "answer": "...",
  "query_text": "...",
  "response_id": "...",
  "cloud_audio_available": true
}
```

Relevant code:

- [`cloud/internal/voice/stream/context.go`](../../cloud/internal/voice/stream/context.go#L155-L184)

If audio generation cannot start, set `cloud_audio_available` to false and return text normally.

### 10.5 Pacing and flow control

For the first buffered implementation, `vic-cloud` may send chunks as they arrive, bounded by local socket send behavior and a maximum response size.

For streaming playback, add explicit receiver feedback rather than sending the whole response as fast as possible. Recommended future control events:

```text
AudioCredit(responseId, allowedBytes)
AudioCancel(responseId, reason)
```

Because `ai_sock` is currently cloud-to-engine only in this usage, production backpressure should use either:

- A new bidirectional local `cloud_audio_sock`, or
- A defined engine-to-cloud control connection.

Do not overload `mic_sock` with response-audio credit messages; it is owned by `vic-anim` microphone control.

## 11. Engine `CloudResponseAudioCoordinator`

Add a dependency-managed engine component:

- `engine/aiComponent/behaviorComponent/cloudResponseAudioCoordinator.h`
- `engine/aiComponent/behaviorComponent/cloudResponseAudioCoordinator.cpp`

### 11.1 Responsibilities

- Receive `CloudMic` response-audio messages from `BehaviorComponentCloudServer` dispatch.
- Validate format, size, response ID, and sequence number.
- Track one active cloud response in the first release.
- Join answer intent and audio lifecycle by `responseId`.
- Forward valid audio to `vic-anim`.
- Expose readiness, playback, completion, failure, and cancellation to behaviors.
- Enforce mutual exclusion with local TTS.
- Drop stale audio from old responses.
- Apply receive, start, completion, and inactivity timeouts.
- Request or signal cancellation when the owning behavior exits.

### 11.2 Proposed states

```cpp
enum class CloudAudioState : uint8_t {
  Inactive,
  WaitingForMetadata,
  Receiving,
  Ready,
  Playing,
  Completed,
  Failed,
  Cancelled
};
```

### 11.3 Public interface

```cpp
struct CloudAudioHandle {
  std::string responseId;
  uint32_t generation;
};

CloudAudioHandle Acquire(const std::string& responseId);
CloudAudioState GetState(const CloudAudioHandle&) const;
bool StartPlayback(const CloudAudioHandle&);
void Cancel(const CloudAudioHandle&, CloudAudioCancelReason);
CloudAudioProgress GetProgress(const CloudAudioHandle&) const;
```

A generation value protects against response ID reuse and stale callbacks.

### 11.4 Ownership rules

- Only one behavior owns a response handle.
- Only one speech renderer may play at a time.
- Acquiring cloud audio does not start playback automatically.
- Starting cloud audio must be rejected while local TTS is active unless the caller first cancels it.
- Releasing or cancelling a handle prevents future chunks from reaching playback.
- Audio arriving without an active or recently expected `responseId` is dropped and logged.

## 12. Engine-to-Anim Messages

Do not reuse the public SDK messages without ownership IDs. Add dedicated robot messages or generalize the player schema.

Proposed messages in:

- [`robot/clad/src/clad/robotInterface/messageEngineToRobot.clad`](../../robot/clad/src/clad/robotInterface/messageEngineToRobot.clad)

```clad
message CloudAudioPrepare {
  string responseId,
  uint_16 audioVolume,
  uint_16 sampleRateHz,
  uint_32 totalFrames,
  bool totalFramesKnown
}

message CloudAudioChunk {
  string responseId,
  uint_32 sequenceNumber,
  uint_16 audioChunkSize,
  uint_8 audioChunkData[1024]
}

message CloudAudioComplete {
  string responseId
}

message CloudAudioPlay {
  string responseId
}

message CloudAudioCancel {
  string responseId,
  uint_8 reason
}
```

The exact fixed-array CLAD syntax should follow generator constraints in this repository. The semantic requirement is a maximum 1,024-byte payload with explicit valid length.

### 12.1 Buffered versus streaming behavior

- In `BufferedComplete`, engine sends `Prepare`, all chunks, and `Complete`; it sends `Play` only when the full response is ready.
- In `Streaming`, engine sends `Play` after the configured prebuffer threshold while more chunks continue arriving.

Using explicit `Play` avoids coupling playback policy to the first-chunk count inside `vic-anim`.

### 14.2 Updated response sequence

After `ConsumeResponse` or `ConsumeIntentGraphResponse`:

1. Store `answer`, `query_text`, `response_id`, and `cloud_audio_available`.
2. If cloud audio is enabled and available, acquire the response handle.
3. Enter the existing `Searching` animation while waiting for audio readiness.
4. If cloud audio reaches `Ready`, select `CloudAudio`.
5. If it fails or misses the readiness timeout, start local TTS generation and select `LocalTts`.
6. For local TTS, transition through `KnowledgeGraphSearchingGetOutSuccess`.
   Ready cloud audio skips this transition (see section 29).
7. Enter `Responding` and start the selected renderer.
8. On renderer completion, play `KnowledgeGraphSuccessReaction`.

### 14.3 Avoid parallel local generation initially

Do not generate local TTS in parallel with expected cloud audio in the first implementation. Parallel generation reduces fallback latency but consumes CPU and memory and complicates cancellation.

Use this policy initially:

- Wait up to 1.5 seconds for buffered cloud audio readiness.
- If unavailable, begin local TTS.
- Once local TTS generation begins, cancel/drop cloud audio for that response.

After measurements, speculative local TTS generation may be added behind a separate setting.

### 14.4 Completion behavior

Cloud playback completion replaces the delegated `KnowledgeGraphTTS` completion callback. The behavior then plays the existing success reaction.

Local fallback continues using `KnowledgeGraphTTS` unchanged:

## 15. Selection and Fallback Policy

Configuration in `knowledgeGraphQuestion.json`:

```json
{
  "cloudAudio": {
    "enabled": false,
    "playbackMode": "BufferedComplete",
    "readyTimeout_ms": 1500,
    "startBuffer_ms": 250,
    "maxDuration_ms": 30000,
    "fallbackToLocalTts": true
  }
}
```

Decision table:

| Condition | Action |
|---|---|
| Feature disabled | Existing local TTS |
| `cloud_audio_available=false` | Existing local TTS |
| Cloud audio ready before timeout | Play cloud audio |
| Invalid format/start/sequence | Cancel cloud audio; local fallback |
| Cloud failure before playback | Local fallback |
| Underflow before meaningful playback | Cancel; local fallback |
| Failure after substantial playback | End gracefully; do not replay full answer |
| User interruption | Cancel; no fallback |
| Behavior deactivation | Cancel; no fallback |

Define “substantial playback” initially as either 750 ms or 20% of known frames, whichever is smaller. This prevents repeating a sentence from the beginning after the user has already heard much of it.

## 16. BufferedComplete First Milestone

### 16.1 Why first

Fully buffering before playback:

- Avoids audible underflow.
- Does not require immediate application-level backpressure.
- Simplifies cancellation and completion.
- Makes audio integrity easy to validate.
- Is still cloud-generated audio.
- Uses the same protocol and player needed for later streaming.

The cost is extra latency equal to cloud TTS generation plus transfer time.

### 16.2 Sequence

```text
KG text result arrives
  -> behavior enters Searching
  -> cloud audio Start/Chunks/End arrive
  -> coordinator validates complete response
  -> anim player is Prepared/filled/Completed-producing
  -> coordinator reports Ready
  -> behavior exits Searching
  -> behavior requests Play
  -> completion callback
  -> success reaction
```

### 16.3 Acceptance target

For typical answers up to ten seconds:

- No audible gaps or truncation.
- Cloud audio begins within the configured readiness timeout or falls back.
- Peak buffered memory remains bounded.
- Interruption stops playback within 150 ms.

## 17. Streaming Playback Second Milestone

### 17.1 Sequence

```text
KG text result + audio Start
  -> receive approximately 250 ms PCM
  -> report Ready and begin playback
  -> continue chunks while playing
  -> maintain target queue
  -> End marks DoneProducingData
  -> Wwise completion reports final success
```

### 17.2 Backpressure requirement

Before enabling streaming in production, implement receiver credit or equivalent flow control. The sender should not enqueue the whole answer immediately.

Recommended credit calculation:

$$
\text{creditFrames} = \max(0, \text{highWatermarkFrames} - \text{bufferedFrames})
$$

Engine or anim reports credit periodically and after crossing watermarks. `vic-cloud` reads or forwards no more than the granted credit.

### 17.3 Underflow policy

- Report underflow separately from completion.
- Allow one short recovery window if Wwise can resume safely.
- Otherwise stop and use the fallback decision table.
- Never append silence indefinitely to hide a failed stream.

## 18. Cloudless Behavior

`vic-cloudless` currently derives Knowledge Graph-style text locally or through its configured path but has no cloud audio source.

Default behavior:

- Set `cloud_audio_available=false`.
- Continue using local `KnowledgeGraphTTS`.
- Compile and understand the new `CloudMic` variants, but do not emit them.

If cloudless later integrates a LAN TTS service, it can emit the same normalized response-audio messages without engine or anim changes.

## 19. Security and Validation

### 19.1 Trust boundaries

- Audio is accepted only from the authenticated `vic-cloud` process/backend path.
- Do not allow arbitrary URLs in the robot protocol.
- Do not log PCM data or full answer text outside existing privacy rules.
- Respect the existing no-logging/data-collection setting.

### 19.2 Required validation

At every layer validate:

- Known response ID
- Supported encoding
- Mono channel count
- Sample-rate range
- Even PCM byte length
- Maximum chunk size
- Exact sequence progression
- Maximum total bytes/frames/duration
- Timeout since last chunk
- Single start and single terminal event
- No chunks after end/cancel

Malformed input results in cancellation and local-TTS fallback when safe.

## 20. Concurrency and Race Handling

### Audio arrives before intent

- Coordinator creates an unclaimed provisional response entry.
- Cap provisional entries at one for the first release.
- Expire after two seconds if no matching intent arrives.

### Intent arrives before audio

- Behavior acquires `responseId` and waits until readiness timeout.
- If timeout expires, select local TTS and mark cloud response cancelled.

### Audio arrives after fallback begins

- Coordinator sees response cancelled or source locked to local TTS.
- Drop all later chunks.
- Do not switch renderer mid-answer.

### Behavior deactivates during receive

- Cancel handle.
- Send `CloudAudioCancel` to anim if prepared.
- Drop future cloud chunks.
- Notify `vic-cloud` when control transport exists.

### Old response arrives during a new question

- Response ID mismatch.
- Drop without changing current state.

### Duplicate or missing chunk

- Duplicate sequence: ignore exact duplicate or fail if payload differs.
- Gap: fail the cloud response; do not attempt PCM concealment initially.

### Process reconnect

- Cancel all active/provisional responses.
- Require a fresh `ResponseAudioStart` after reconnect.
- Never resume a partially received response across process restart.

## 24. Acceptance Criteria: BufferedComplete Release

The first release is complete when:

- Both Knowledge Graph paths can play cloud-generated PCM.
- The answer text is always available and local TTS remains functional.
- Feature-disabled behavior is unchanged.
- Audio is transported in bounded chunks, not in intent JSON.
- Playback begins only after the complete response is validated.
- Touch, fall, pickup, and behavior deactivation cancel playback.
- Failure before playback falls back to local TTS.
- Stale or malformed audio never plays.
- Audio length and memory are bounded.
- Completion drives the existing Knowledge Graph success reaction.
- Automated tests cover ordering, cancellation, fallback, and stale-response races.
- Hardware tests show no audible gaps or truncated normal completion.

## 25. Acceptance Criteria: Streaming Release

Streaming playback is complete when:

- Playback starts after a configurable 150–300 ms prebuffer.
- Remaining audio arrives while playback continues.
- Application-level backpressure prevents excessive queue growth.
- Underflow and overflow are separately observable.
- Cancellation propagates to cloud generation and robot playback.
- First-audio latency improves measurably over buffered mode.
- Network jitter tests meet the defined completion/underflow target.

## 26. Key Risks and Mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| Chipper API cannot return audio | Backend work blocks robot integration | Transitional `vic-cloud` TTS client; fake provider for tests |
| Intent and audio arrive in different order | Wrong fallback or stale playback | Response ID join with provisional state and timeout |
| Existing process closes stream after intent | Audio truncated | Separate upstream stop from downstream completion |
| Datagrams are too large | Truncation/corruption | Maximum 1,024-byte payload; packed-size tests |
| Streaming plugin starves | Audible gaps | Buffered first release; prebuffer and credit before streaming |
| Cloud response fails after partial playback | Repeated or incomplete answer | Meaningful-playback threshold; do not replay entire answer |
| Local TTS and cloud audio overlap | Two voices/audio conflicts | Single engine coordinator and explicit renderer ownership |
| Old answer plays for new question | Severe UX/privacy failure | Mandatory response IDs, generations, and cancellation on new turn |
| Audio data consumes excess memory | Stability issue | Duration/byte caps and one active response |
| Cloud audio leaks into future full-duplex mic input | Recognition failure | Future final-speaker-mix AEC reference; not solved here |

## 27. Design Decisions

- Integrate cloud audio with Knowledge Graph before general voice responses.
- Preserve both prompted and bypass input paths.
- Keep answer text mandatory.
- Use chunked transport for buffered and streaming playback.
- Deliver a fully buffered PCM mode first.
- Add true streaming only with prebuffer, status, and backpressure.
- Add a first-class internal cloud-audio coordinator and player.
- Reuse lower-level SDK streaming mechanisms, not the public SDK RPC as the permanent internal protocol.
- Use a dedicated plugin ID and Wwise event.
- Keep local TTS as deterministic fallback.
- Correlate every asynchronous operation with `responseId` and generation.
- Treat cloud audio as output only; it does not itself provide full duplex.

## 28. Implemented low-latency interruption handling

Lycopod defaults `knowledge.cloud_audio_first_sentence` to **true** and publishes
the first sentence/audio handle before `tts.stop`. Explicit `false` still buffers
the entire answer, trading latency for suppression of all audio on a later abort.
Already played audio cannot be retracted in first-sentence mode.

The previous raw HTTP path collapsed late upstream failures into a Provider
error in `cloud/internal/voice/cloudaudio.go`. UIC retained only an error boolean,
and KG could repeat early partial speech via local TTS or drain a longer failed
answer through renderer completion. Aborted published handles were also deleted
before a delayed fetch could learn their outcome. The changes below preserve
the outcome through each of those boundaries rather than treating failure as EOS.

For handle-based GET requests, `vic-cloud` now negotiates
`Accept: application/vnd.lycopod.answer-audio.v1`. A matching Content-Type enables
framing: one-byte kind, four-byte big-endian payload length, payload. PCM kind 0
has 1–1024 bytes; terminal kinds have no payload: 1 successful END, 2 upstream
abort, 3 upstream connection loss/timeout, 4 producer failure. No new CLAD fields
or enum values are needed: existing `ResponseAudioErrorType::Cancelled` and
`Transport` convey the two interrupted outcomes with stream/response ownership.

HTTP 200 cannot change after publication and is not an answer outcome. Framed
EOF without END, a truncated frame, or incomplete HTTP transfer is a transport
failure; no padding, successful `ResponseAudioEnd`, or renderer completion is
fabricated. Partial legacy raw-body failure is also Transport, but cannot tell
explicit abort from connection loss. Generic text-to-TTS POSTs and old raw
servers remain supported. Authentication/status/connection-establishment errors
before an audio response, malformed audio and ordinary provider failures retain
normal fallback policy rather than being globally silenced.

Before publication, lycopod's typed upstream cancellation remains empty KG or
terminal `intent_system_noaudio` in initial IntentGraph fallback. After
publication it clears retained PCM but preserves the cancelled record until
consumption/eviction, so a delayed HTTP fetch does not get a misleading 404.
Negotiated interrupted records work even before any PCM reaches the robot.

UIC preserves the typed interruption, rejects readiness, clears pending PCM and
does not mark completion. KG observes it in searching, at playback admission and
during streaming: cancel the renderer, clear queues, mark the conversation
unsuccessful, exit quietly without a failure animation, local TTS or automatic
follow-up. This policy also covers an established producer's readiness deadline
or playback stall, but not a fetch that never established an audio response.
It is independent of follow-up being enabled and of the one-turn limit.
Other failures never drain partial audio as if successful; the old
meaningful-playback threshold is retained only for ordinary local-TTS fallback.

Migration requires updated lycopod and **both vic-cloud and vic-engine**.
Install via the project's consistent full OTA workflow after review; no
packaging, robot installation or service restart is performed by this change.
Existing raw clients do not gain typed post-header cancellation by updating
lycopod alone. Existing `cloud_audio: false` SDK behavior is unchanged.

Validation for this change: 155 targeted lycopod tests (including real KG and
IntentGraph RPC early return followed by streamed abort/connection loss, real
WebSocket truncation, buffered mode, and disabled cloud audio); 24 Go voice tests
plus 27 subtests and three KG/follow-up adapter tests under `-race`; 41 native
production-routing/session/playback tests under ASan/UBSan. The native harness
executes the real UIC and KG searching/admission/streaming/cancellation functions,
including interruption before playback, before/after the old salvage threshold,
follow-up disabled and one-turn policy, and established versus unopened readiness
timeouts.

Both actual ARM `vic-engine` (including `libcozmo_engine.so`) and `vic-cloud`
built in the existing offline Yocto builder. Evidence and artifact hashes are
under `anki/victor/_build/interruption-validation/`, with native results under
`anki/victor/_build/kg-followup/`. The initial host build lacked the cross
compiler; the container build required the existing writable caches and explicit
release/tool definitions (this project's CMake clears stale command-line
definitions on regeneration). Final incremental ARM build succeeded. No version
bump, packaging, installation or hardware/acoustic validation was performed.

## 29. Cloud audio starts without waiting for search animations

While `Searching` with a cloud response, `BehaviorUpdate` checks readiness,
errors, and the existing readiness deadline on every behavior update. Once
actionable, it calls `CancelDelegates(false)` to suppress the cancelled search
animation's completion callback and reuses the existing readiness/error path.
Ready cloud audio transitions directly to `Responding` and starts its renderer,
without `KnowledgeGraphSearchingGetOutSuccess`.

This can interrupt either the initial searching get-in/loop sequence or a later
loop. The packaged asset manifest lists the searching loop as 1,188 ms and its
success exit as 297 ms; neither is now a prerequisite for cloud playback. These
are animation durations, not measured end-to-end latency savings.

The 24,000-byte prebuffer (750 ms of 16 kHz mono PCM16), completed-short-answer
readiness, playback pacing, response ownership, and local-TTS animation path are
unchanged. Cancellation/transport errors still stop quietly; ordinary failures
retain the existing local fallback policy. Readiness deadlines are no longer
delayed until a search animation callback.

The existing production-extraction routing harness covers a buffer crossing the
unchanged threshold between updates, callback-disabled cancellation, immediate
PCM submission with no exit delegation, no duplicate renderer preparation,
unchanged local-TTS delegation, and error/deadline handling during search.
This is a robot-firmware change only; no Lycopod changes are required.

Cloud-answer admission also omits the Knowledge Graph end earcon
(`Wake_Word_Success`). The decision is made after consuming either the prompted
or bypass response, so a valid cloud answer starts without this extra chime.
Local-only/disabled-cloud responses and missing answers retain the earcon;
wake and listening-start cues are unchanged. Later cloud failure retains the
existing fallback policy without inserting a delayed acknowledgement.

## Wake-word interruption

`wakeWordBargeInEnabled` in `knowledgeGraphQuestion.json` enables coordinated
wake-word interruption during cloud-answer playback. It defaults to `true`,
including when omitted and in the packaged behavior configuration.
Set it to `false` to opt out and restore the prior playback behavior.
Picovoice remains the wake backend. This does not enable adaptive AEC or change
`ANKI_AEC_EXPERIMENT=reference`.

During a cloud answer, say the wake word, wait for the listening cue/indicator,
then give the new command. Words spoken immediately after the wake word while
the old answer is stopping are deliberately not retained. This is interruptible
half-duplex, not simultaneous ASR of speech over the answer. The new request is
`Normal` / IntentGraph, not an automatic KnowledgeGraph follow-up, so it can
also be a non-question command.

The implementation uses the existing trigger-response stack and capture
protocol, with playback-tagged notification-only wake responses:

1. The KG renderer arms a notification-only response for its playback ID.
   Animator emits at most one tagged wake notification for that ID, without
   starting an earcon, get-in animation, or microphone stream. This is voice
   only: a button press does not create a replacement capture through this
   override; existing touch interruption remains separate.
2. KG accepts only its current, armed playback while responding. It ends the
   current conversation, suppresses delegated callbacks, cancels the renderer,
   clears buffered PCM, and stops the old stream. UIC rejects old stream
   results; vic-cloud invalidates the owner and cancels its HTTP download.
3. KG waits for the matching renderer `Cancelled` (or an already-completing
   `Completed`) acknowledgement, then at least 250 ms of settling. It also
   requires the old capture's closed acknowledgement. Repeated notifications
   and stale playback IDs cannot restart capture.
4. It removes only its own trigger override and requests a fresh ordinary wake
   command, using the existing listening get-in/earcon. Capture begins after
   the earcon and uses the existing sequence/time fence with zero pre-roll,
   excluding queued old answer audio. Normal wake-intent dispatch takes over.

Mute, engine wake locks, pickup, superseding capture, behavior deactivation,
or a three-second stop/settle timeout abort the handoff without opening a
replacement capture. Playback completion, local fallback, failure and
deactivation remove the override. Local-TTS playback and the ready/search
phases are outside this feature. Automatic follow-up remains independent.

**Acoustic limitation:** reference mode supplies a reference but does not cancel
speaker echo. Picovoice can miss a user's wake during loud playback or detect
the robot saying its own wake phrase. Playback identity and one-shot delivery
prevent stale/repeated protocol handoffs; they do **not** identify the speaker
or reject acoustic self-wakes. There is no new Picovoice playback-reference
recognizer or claim of echo-safe duplex here. Default-on does not remove the
need for robot acceptance, including answers containing the wake phrase,
different volumes/distances, mute/pickup and repeated interruptions. The
configuration opt-out remains available if acoustic self-wakes are a problem.

The engine/animator CLAD message layout changes require matching firmware
components; do not deploy just one process from this revision. No Lycopod
changes are required. OTA builds must include the matching engine, animator
and cloud worker; building an image does not install it on the robot.
